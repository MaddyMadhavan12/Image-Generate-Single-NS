Note on run-to-run variance: readiness times for the same service can legitimately differ between runs. Common causes include node-level image cache state, scheduler/node placement (a pod landing on a busy or newly-scaled node takes longer), API server / etcd load when many events fire close together, and cluster autoscaler activity.
Cached vs Not Cached: this is determined from the pod's actual Kubernetes events for this run, not from the requested Pull Type. If the node already had the image, kubelet emits "already present on machine" and the row shows Cached with no pull time. If a real pull happened, the row shows the measured pull duration (e.g. 16s) plus a Not Cached label.
What is "Other Events"? Small bits of time between the 6 tracked steps (Scheduling, Image Pull, Istio Pull, Container Create, Container Start, Readiness) that don't belong to any one step specifically. It's already counted in the Total Ready Time shown — not extra time, not missing time, just leftover time that doesn't fit neatly into one of the 6 named steps.
